## What each piece is for

**`packages/protocol-spec/`** holds `constants.json` — the single source of
truth for every protocol constant — and `vectors.json`, a committed set of 135
test cases generated by the Python implementation. The vectors are the
*contract* between the two languages: neither implementation merges a change
without reproducing them byte for byte. That is what stops the app and the
server quietly disagreeing about what a token is, which would produce matches
that silently never happen.

**`packages/protocol_py/`** is the reference implementation, and the server
imports it directly. The server's tests never mock it: a server test that
built tokens with a stand-in would prove nothing about the real system.

**`packages/protocol-ts/`** is the same bytes in TypeScript, because the app
has to build its own tokens. It cannot delegate to the server — if the server
could build a user's tokens, it could read their interest.

**`server/`** is deliberately the least interesting component. It stores
accounts, pairs up tokens, bakes digests and relays messages. Its most
important property is everything it cannot do: §3 and §4 explain why.

**`app/`** is where the cryptography actually matters, because it holds the
keys. The native Kotlin module is kept as thin as possible — advertise, scan,
count, persist — and contains **no cryptography at all**. Ephemeral ids are
derived in TypeScript and handed down as a schedule, so the private keys never
cross the bridge.

**`sim/`** is independent of all of it. It exists because the real system makes
its own research question unobservable: the concentration of *one-sided*
interest cannot be measured in a system that refuses to record one-sided
interest. See §8.

## The three boundaries that matter

1. **`app/src/api/client.ts`** is the only file allowed to touch the network.
   ESLint forbids `fetch` and `XMLHttpRequest` everywhere else, and
   `app/scripts/check-privacy-invariants.ts` independently greps for them, so
   disabling the lint rule is not enough to ship a second network path.

2. **The JS/Kotlin bridge** carries a schedule down and window counts up.
   Never a key, never an RSSI value, never a timestamp. The TypeScript wrapper
   copies the five allowed fields out of each native sighting explicitly rather
   than spreading the object, and a test feeds it a stray `rssi` field to prove
   it is dropped.

3. **The wire** carries only padded sets of opaque 32-byte values. The presence
   upload body has exactly one field. The signal upload body has exactly one
   field. That is the whole protocol surface through which interest could
   conceivably leak, and it is the reason both tests that check it are the two
   most important tests in the repository.

## Why the tiers

The work is split so that the research result does not depend on the hardware:

- **Tier 1** — protocol, server, leak tests, simulation, documents. No phones,
  no users. **Complete and defensible on its own**, which it now is.
- **Tier 2** — the Android app and the real BLE work. Needs two phones for one
  phase.
- **Tier 3** — the field pilot. Needs ethics approval, and is gated
  mechanically: the server refuses to start in study mode without one.

The ordering is not project-management decoration. The BLE layer rests on an
Android behaviour nobody can promise in advance — whether an advertisement is
still delivered to a scanner that has declared `neverForLocation` and holds no
location permission. If the answer turns out to be no, Tier 2 needs rethinking
and Tier 1 is untouched. `docs/BLE_SPIKE.md` is the measurement protocol, and
its results tables are deliberately still blank.
