## 1. What this project is

Mutual is a campus connection app and a research prototype. Students' phones
quietly notice — over Bluetooth, never GPS — which other students they actually
spent time near. Each morning a student sees yesterday's "crossings" (never
where, never live), and can send a private **signal** to any of them for one of
five intents: study, project, fitness, friend, date. If both people signal each
other for the same intent, both are told the next morning. If not, **nobody
ever learns the signal existed — not the other person, and not the server.**
Photos are never shown while browsing; they are revealed only after a mutual
match.

The research has three parts (see `SPEC.md` §3):

1. **A private matching protocol** whose server provably learns nothing about
   one-sided interest. This is the core contribution.
2. **A simulation** of how photo-reveal timing affects how unequally attention
   is distributed among users.
3. **A small field pilot** comparing two reveal policies — **gated** behind
   written ethics approval. No real-user research data may be collected until
   that approval exists (see §5, invariant 9).

The work is split into tiers (`SPEC.md` §4). **Tier 1 is a complete,
defensible research result on its own** — protocol, server, leak tests,
simulation — and needs no phones and no users. Protect Tier 1 above all else.

This is an unaudited research prototype. Never describe it, in code comments,
docs or UI copy, as production-ready or as having been security-audited.

## 2. Hard constraints

- **Zero budget.** No paid API, paid service, paid dataset or paid compute.
  Every dependency must be free and open-source. If something requires a paid
  plan, stop and flag it in `PLAN.md` instead of using it.
- **Runs on one Windows laptop.** Development happens on Windows with
  PowerShell. Every script must run on Windows. Use Python or Node for
  scripting, never bash-only scripts. Use `pathlib` / `path.join`, never
  hard-coded `/` path strings.
- **Android only (minSdk 31, Android 12+).** iOS is out of scope (see `SPEC.md`
  decision D1). Do not add iOS-specific code paths.
- **No GPS or location, ever.** See invariant 3.
- **Two physical Android phones are needed only for Phase 9 (real BLE).** All
  other phases must be fully developable with emulators and the fake BLE
  adapter.

`server` and `sim`.

```powershell
# Python setup (once)
py -3.11 -m venv .venv            # python.org install of 3.11
uv venv --seed --python 3.11 .venv   # uv-managed 3.11 (this laptop; SPEC Q7)
.venv\Scripts\Activate.ps1
pip install -e packages/protocol_py -e "server[dev]" -e "sim[dev]" pre-commit
pre-commit install

# Python tests
pytest packages/protocol_py server sim -q
python -m mutual_protocol.vectors --out packages/protocol-spec/vectors.json

# Node setup (once, from repo root)
npm install

# TypeScript protocol tests and strict typecheck
npm test -w packages/protocol-ts
npm run typecheck -w packages/protocol-ts

# Server (dev mode: OTP codes printed to console, dev routes enabled)
$env:MUTUAL_ENV="dev"; uvicorn mutual_server.main:app --reload --app-dir server

# Database migrations
alembic -c server/alembic.ini upgrade head

# Simulation
python -m mutual_sim.run --config sim/config.yaml --seeds 30
python -m mutual_sim.sweep --config sim/config.yaml

# App
npm run lint -w app
npm test -w app
npm run check:privacy -w app      # privacy invariants script
npm run check:contrast -w app     # design-token contrast check
npx expo run:android              # run from app/; builds the dev client

# Everything fast, before any commit
pre-commit run --all-files
```

If a command here turns out to be wrong for the installed tool versions, fix
it **here** and in `SPEC.md` in the same change — do not silently use a

## 5. Privacy invariants — NEVER violate these

These are the whole point of the project. A feature that requires breaking one
is a spec change that only the human can approve. If you notice existing code
that violates one, stop and report it before doing anything else.

1. **No attention-dependent network traffic before a match.** Never add a
   network request whose existence, timing, size, order or parameters depend on
   which profile a user viewed, opened, scrolled to, played or signalled —
   before a mutual match exists. Digest media is always prefetched in full by
   `app/src/digest/prefetch.ts`; UI components read media from the local cache
   only and never call the network.
2. **Signals leave the device only as the epoch's padded set.** Exactly `K`
   tokens (from `constants.json`), shuffled with a CSPRNG, uploaded at most
   once per epoch, at a random time inside the upload window. Never upload a
   single signal, never upload early "because the user just tapped", never
   include intent, peer id or count in any request.
3. **No location.** Never request `ACCESS_FINE_LOCATION`,
   `ACCESS_COARSE_LOCATION` or `ACCESS_BACKGROUND_LOCATION`. Declare
   `BLUETOOTH_SCAN` with `usesPermissionFlags="neverForLocation"` and block the
   location permissions in the Expo config. If BLE does not work without a
   location permission, **stop and escalate** — never add it as a workaround.
   Daily keys, ephemeral private keys, EIDs, RSSI and sighting times are
   **never sent over the network** (EIDs are only broadcast over BLE).
   Presence uploads contain only the padded, secret-keyed encounter-token set
   (`SPEC.md` §6.13).
4. **No real-time proximity.** Crossings become visible only in the next
   morning's digest (after `digest_release_time`). Never show who is nearby
   now. Never show a place name. Never show crossing counts or exact times —
   only a coarse block (morning/afternoon/evening/night) computed on-device.
5. **Minimal storage of identity data.** Never store plaintext email, date of
   birth, OTP codes or session tokens. Store keyed hashes and an
   `age_verified_at` timestamp only. Never log or store client IP addresses
   or user agents (run uvicorn without its access log).
6. **No third-party analytics, crash reporting or ad SDKs.** No Firebase
   Analytics, Sentry, Amplitude, Mixpanel, Segment or similar. The denylist is
   enforced by `app/scripts/check-privacy-invariants.ts`.
7. **No home-made cryptography.** Only compose audited primitives: Python
   `cryptography` (X25519) and stdlib `hashlib.blake2b`; TypeScript
   `@noble/curves` (x25519) and `@noble/hashes` (blake2b). Never implement a
   primitive, never use `Math.random()` or `random` for anything
   security-relevant, compare secrets with constant-time functions
   (`hmac.compare_digest`).
8. **Protocol bytes change only through the spec.** Never change any byte
   format, personalization string, constant or derivation without, in the same
   change: updating `SPEC.md` §6, updating `constants.json`, bumping
   `protocol_version`, regenerating `vectors.json`, and passing both the Python
   and TypeScript suites.
9. **No research data from real people without approval.** Never enable
   `study.enabled`, never write code that exports real-user data for analysis,
   and never recruit or message real users for research unless
   `study.approval_reference` is set and `study/APPROVAL.md` exists. The server
   must refuse to start in study mode otherwise. Development and testing use
   synthetic accounts only.
10. **No per-peer endpoints before a match**, except the explicit,
    user-initiated safety actions: block and report. Every route taking a peer
    or user id must return a uniform error unless a **notified** match exists
    (or it is block/report, which always return the same 204).
    `server/tests/test_route_audit.py` enforces this.
11. **Dev-only routes never ship.** `/v1/dev/*` (clock travel, simulated
    crossings) exists only when `MUTUAL_ENV=dev` and is tested to be absent
    otherwise.
12. **Fair match delivery.** Matching runs only in the nightly batch, never
    inside a request. Before `notify_after`, no response to anyone may depend
    on whether a match exists. After it, a match cannot be erased for one side:
    unmatch or block leaves an `ended` match for the other party (`SPEC.md`
    §6.9).
13. **Campus isolation.** No query, digest, crossing, signal match, block,
    report or media access may ever span two campuses (`SPEC.md` §4.1). A
    new college opens only after the operator approves it.

## 6. Conventions

### Python (protocol_py, server, sim)
- Python 3.11. Type hints on every function signature. `ruff` for lint and
  format. `pytest` for tests.
- Pydantic v2 models for every request and response body. SQLAlchemy 2.x
  typed ORM. Alembic for every schema change — never edit the DB by hand.
- Time: never call `datetime.now()` directly in server logic. Use the injected
  clock (`mutual_server.clock`) so tests and dev time-travel work.
  All "day" and "epoch" values are dates in the configured timezone
  (`Asia/Kolkata` by default), formatted `YYYY-MM-DD`.
- Every tunable number lives in `server/config.yaml`, `sim/config.yaml` or
  `packages/protocol-spec/constants.json` — never inline in code.
- Docstrings state units (bytes, seconds, minutes, dBm).

### TypeScript (protocol-ts, app)
- `strict` TypeScript. No `any` without a comment explaining why.
- All network calls go through `app/src/api/client.ts`. ESLint forbids
  `fetch` and `XMLHttpRequest` everywhere else.
- All colours, spacing, radii, type sizes and durations come from
  `app/src/design/tokens.ts`. No raw hex values or magic numbers in
  components (the privacy/lint script checks for hex literals in
  `app/app/` and `app/src/components/`).
- Bytes are `Uint8Array`. Wire encoding is base64url without padding,
  implemented once in `protocol-ts/src/encoding.ts`.

### Kotlin (app/modules/mutual-ble)
- Keep the native module minimal: advertise, scan, foreground service,
  sighting aggregation, persistence. No cryptography in Kotlin — ephemeral IDs
  are computed in TypeScript and handed to native as a schedule.

### UI principles (see `SPEC.md` §13 for the full design system)
- **The interface is the human's top priority.** Every screen must match
  `docs/design/prototype.html` exactly, in both themes (SPEC §13.9, D19). Open
  it side by side with the emulator before calling any screen done. Never
  "improve" the design on your own initiative; propose changes instead.
- No swipe decks, no streaks, no badges, no "likes" counts, no
  "X people want to meet you" teasers, no urgency copy. Calm, warm, honest.
- Respect the OS reduce-motion setting and font scaling everywhere.
- Every screen works in light and dark themes.

## 7. Tests

- A phase is not done until its tests pass **and** the human has reviewed the
  diff. Passing tests are necessary, not sufficient.
- Never weaken, skip, or delete a test to make it pass. If a test encodes the
  wrong behaviour, that is a spec problem — see §8 rule 3.
- Protocol changes must pass the cross-language vector suite in both
  languages.
- Never mock the protocol package in server tests. Server tests use the real
  `mutual_protocol` to build tokens and EIDs.
- The two privacy tests — `test_leak_two_worlds.py` and
  `test_route_audit.py` — are the most important tests in the repository.
  Treat any change that touches them with extra care and say so in the
  commit message.

## 8. Spec-driven discipline

The workflow is spec → plan → implement → verify → iterate.

1. **No implementation before an approved plan.** `PLAN.md` must exist and the
   human must have explicitly approved the phase you are about to start.
2. **One phase per session, one phase per approval.** Implement only the
   phase the human named. Stop at the end of it for review. Never "also start"
   the next phase.
3. **Fix the spec, not the code.** If a test fails or behaviour does not match
   intent, first decide whether the spec is ambiguous, wrong or incomplete. If
   it is, propose the exact `SPEC.md` wording change, wait for approval, then
   re-implement. Never patch code around an ambiguity.
4. **Never invent results.** Simulation outputs, BLE detection rates, battery
   numbers and pilot results are measured and reported as they are —
   including null and negative results. Never tune parameters after seeing
   results in order to produce a preferred conclusion; any parameter change
   after results exist must be recorded in the Progress log with the reason.
5. **Flag scope creep.** If a phase starts requiring changes outside its
   listed files, stop and ask.
6. **Record what you measure.** Spike results, timings, version pins, and any
   deviation from the plan go in the `PLAN.md` Progress log before the
   session ends.
7. **When in doubt, ask.** Privacy, safety, the study gate, and anything
   irreversible always warrant a question rather than a guess.
8. **Keep `docs/DECISIONS_LOG.md` current.** Every time you ask the human a
   question, a review reports findings, or an idea is raised, add a
   plain-language entry in the same session: what came up, the options, what
   was decided, by whom, and where it landed in the spec. Keep its Board (open
   questions, parked ideas) up to date. Pure security fixes may be applied
   without asking (the human's standing delegation, 2026-10-05), but they
   must still be logged there.
